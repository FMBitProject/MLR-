Findings in detail

High Fixed

A verdict was reported over an empty evidence set

journal-corpus.ts

chunkDocument() short-circuited on content.length <= CHUNK_CHARS with return [content], ahead of the .filter(Boolean) that guards the long-document path. A document whose stored content was empty therefore produced one empty-string chunk instead of none.

Why it matters — and why High Downstream in journal-check.ts, chunks.length was then truthy, so the no-LLM branch returned verdict abstract_only with an empty note. A reviewer deciding whether a claim is substantiated saw what looked like a completed check with a blank excerpt, rather than “no readable source”. Presenting an empty result as a performed check is the one failure mode in this suite that can actively mislead a regulated decision — everything else merely wastes time or looks untidy.
Fix Both paths now trim and drop empties, so a blank document yields no chunks and the substantiation falls through to its existing “unavailable” state. Three regression tests cover empty content, whitespace-only content, and a blank document sitting alongside a real one.
Medium Fixed

The substantiation check hard-failed instead of degrading

journal-check.ts

checkAgainstJournal() wrapped no part of its corpus resolution in try/catch. Every other failure in that module degrades to null — the module's stated contract is that AI assistance is always optional — but a database or lookup error thrown by ensureJournalDocument() propagated straight out.

Why it matters The calling server action has a designed unavailable state for exactly this situation, and never reached it: one unreadable reference aborted the whole action, the flag was left un-updated, and the reviewer got a generic server error instead of an honest “could not verify”.
Fix Each reference lookup is now individually guarded and logged, so one bad reference is skipped and the remaining candidates still resolve. A total failure lands in the existing unavailable state rather than erroring out of the reviewer's action.
Medium Fixed

Unsanitised user text in outbound email subjects

email.ts

The audit began at sendInviteEmail(), which escapes the workspace name in the HTML body but interpolated it raw into the subject. Reading the rest of the module showed the same pattern at several more call sites — submission titles flow unescaped into review-request and decision subjects too.

Why it matters — and what it is not This is not an injection hole. A subject is not rendered as markup, and Resend takes it as a JSON field rather than concatenating SMTP headers, so CRLF header injection is not reachable. What is real: a workspace name or submission title containing newlines, or running to hundreds of characters, produces a mangled subject line in every recipient's inbox.
Fix Sanitising moved to the sendEmail() boundary rather than the one call site that surfaced it — whitespace runs collapse to single spaces and the subject is capped at 180 characters with an ellipsis. One change covers all present and future callers. Four tests cover newlines, over-length truncation, a non-invite call site, and an ordinary subject passing through untouched.
Medium Fixed

The SOP revision-header filter never fired

claims-extract.ts

The heuristic extractor filters document headers with /\brev\.?\s*\d/i, but the sentence splitter ran first and split on (?<=[.!?])\s+. “Dokumen ini Rev. 3 berlaku sejak…” was already cut at the period in “Rev.” before the filter saw it, and the leading-number strip then turned the tail into a clean-looking sentence. The filter was effectively dead code.

Why it matters SOP revision boilerplate leaked into the claim-import candidate list. A human ticks which candidates become approved claims, by design, so nothing wrong could be published — but it is avoidable noise in a screen meant to be scanned quickly, and a dead filter reads as working.
Fix The splitter no longer breaks on the period of a reference abbreviation (Rev., No., Vol.…), so the sentence reaches the header filters intact. Tests cover the revision marker, a second abbreviation, and that an ordinary sentence boundary still splits normally.
Low Fixed

English relative dates read “1 days ago”

i18n.ts

relativeDays() had no singular branch. Its sibling daysUntil() in the same file already special-cases 1 (“1 day left”), so this was an inconsistency rather than a deliberate choice. Indonesian is unaffected — it does not inflect for number.

Why it matters Purely cosmetic, but it appeared on every dashboard, activity log and reminder digest for English-locale users.
Fix A singular branch mirroring daysUntil(). Three tests cover the singular, the agreement between the two sibling helpers, and that every other count still pluralises.
Low Fixed

The same pluralisation bug in the content-expiry digest

email.ts

Found while checking what depended on relativeDays(): the expiry digest formats its own day counts rather than reusing the helper, and had the identical defect on both sides — “expired 1 days ago” and “1 days left”. Both counts are reachable, since daysLeft comes from a Math.ceil that returns 1 and −1 routinely.

Why it matters Same cosmetic weight as the one above, but it lands on the material closest to needing action — the item expiring tomorrow, or that expired yesterday, is exactly the row a compliance admin reads first.
Fix Inflection applied to both the past and future branches, English only. Two tests cover the English singular and plural forms on both sides, and that Indonesian stays uninflected.

What is not covered, and why

These are deliberate exclusions, not oversights. Each needs a live Postgres or a Next.js request context, which makes it an integration test rather than a unit test.

actions.ts 1,948 lines of "use server" actions. Every one opens with requireUser() (cookies) and queries the database. The single largest coverage gap in the app, and the one most worth an integration suite.
reminders.ts · notify.ts
content-expiry sweep
billing sweep Cron fan-out. The pure parts — contentLifecycle, billingState, addOneMonth — are covered above; the sweeps themselves query, send, and write back.
throttle.ts The rate limiter is one atomic SQL upsert. Its correctness is in the SQL, so a unit test with a mocked db would assert nothing real.
account-tokens.ts
audit.ts · audit-query.ts
usage.ts · storage.ts Thin database wrappers. Token TTLs (24 h verify/invite, 1 h reset) and audit append-only behaviour are worth asserting — against a real schema.
auth.ts (sessions)
i18n-server.ts Cookie signing and reading need next/headers inside a request scope. Role constants and separation-of-duties are covered.
components/ · app/ React components and route handlers. No renderer is installed; adding one is a larger decision than this task.

The new guard in checkAgainstJournal() is exercised only indirectly here: proving it degrades correctly needs a database that can be made to fail on demand. Asserting it at unit level would mean depending on Postgres being absent, which would silently invert the moment someone runs docker compose up. It belongs in the integration suite.

Running it

# from app/
npm test          # 239 tests, ~6s, exit 0
npm run test:watch
  • Node's built-in runner via tsx — no new dependencies. Both were already in the project.
  • tests/setup.ts is preloaded with --import. It sets a dummy DATABASE_URL so DB-importing modules load; the pg pool is lazy, so nothing dials Postgres. Any test that did issue a query would fail loudly with ECONNREFUSED rather than quietly hitting a real database.
  • Tests get their own tests/tsconfig.json and are excluded from the app's. npx tsc --noEmit is clean for both — the Next build is untouched.
  • Network calls are stubbed per test by swapping globalThis.fetch and restoring it in finally. No test reaches NCBI, Midtrans, Resend, or any LLM provider.
  • PPTX and DOCX fixtures are built as real ZIP archives with JSZip, so the extractors run against genuine Office file structure rather than a hand-rolled mock.
